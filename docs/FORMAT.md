# ULocker 容器格式规范 v1

本文是 `.ulocker` 容器的完整字节级规范。实现者只要照着本文就能写出兼容的读写程序
（`ulocker/vault.py` 是参考实现）。

约定：**大端序**，所有整数均为无符号。偏移均以文件开头为原点。

---

## 1. 总体布局

```
┌────────────────────────────────────────────────────────────────────┐
│ 0   ‥ 头部（含加密索引）                                            │
│        ├─ 明文区：魔数 / 版本 / KDF 参数 / 数据区偏移（全部参与 AAD） │
│        └─ 密文区：索引密文（AES-256-GCM）                           │
│ 零填充到「数据区起始偏移」                                          │
├────────────────────────────────────────────────────────────────────┤
│ 数据区起始偏移 ‥ 文件末尾                                            │
│        分块记录 0、分块记录 1、…（每个条目的记录连续排列）            │
└────────────────────────────────────────────────────────────────────┘
```

头部是**变长**的，所以「数据区起始偏移」显式写在头部里；头部的实际长度由字段累加得到，
两者的差值就是零填充的长度。这一块预留空间的作用是：以后索引变大（追加条目、改名）时
可以原地重写头部，而**不需要搬动数据区**。

---

## 2. 头部字段

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 8 | `magic` | 固定 ASCII 字符串 `ULOCKERV` |
| 8 | 1 | `version` | 格式版本，当前为 `0x01` |
| 9 | 1 | `kdf_id` | `0x01` = Argon2id，`0x02` = scrypt |
| 10 | 2 | `flags` | 见下表 |
| 12 | 2 | `kdf_params_len` | `kdf_params` 的字节长度 `L` |
| 14 | L | `kdf_params` | UTF-8 编码的 JSON 对象 |
| 14+L | 8 | `data_offset` | 数据区起始的绝对偏移，必须是 4096 的整数倍 |
| 22+L | 12 | `index_nonce` | 索引密文使用的 GCM nonce |
| 34+L | 4 | `index_ct_len` | 索引密文长度 `M`（含 16 字节 GCM 认证标签） |
| 38+L | M | `index_ct` | 索引密文 |
| 38+L+M | — | 零填充 | 一直到 `data_offset` |

### flags

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `DRIVE_BOUND` | 容器绑定了某个特定卷（卷序列号）。只是给人看的提示位，真正的绑定信息在索引里 |
| 1 | `ZLIB` | `index_ct` 解密后再做一次 zlib 解压才得到索引 JSON |
| 2‑15 | — | 保留，必须为 0 |

### kdf_params

JSON 对象，字段随 `kdf_id` 而变，**始终包含 `salt`**（Base64 编码的 16 字节随机盐）：

```jsonc
// kdf_id = 1 (Argon2id)
{ "salt": "…", "time_cost": 3, "memory_cost": 65536, "parallelism": 4 }

// kdf_id = 2 (scrypt)
{ "salt": "…", "n": 32768, "r": 8, "p": 1 }
```

### 附加认证数据（AAD）

`index_ct` 的 AAD 是**从文件偏移 0 到 `index_ct_len` 字段结束**的全部字节，即：

```
AAD = magic ‖ version ‖ kdf_id ‖ flags ‖ kdf_params_len ‖ kdf_params
      ‖ data_offset ‖ index_nonce ‖ index_ct_len
```

也就是说上面表格里 `index_ct` 之前的每一个字节都被密码学保护了。任何篡改
（改版本号、改 KDF 参数、把 `ZLIB` 位翻一下、把 `data_offset` 挪走）都会导致
解密直接失败，而不会静默地产生错误行为。

---

## 3. 密钥派生与分层

```
口令 (UTF-8)
   │  Argon2id / scrypt，salt 来自头部
   ▼
  KEK (32 B)
   │  HKDF-SHA256，info = "ulocker/v1/index"
   ▼
index_key (32 B) ──AES-256-GCM──▶ 解密 index_ct，得到索引 JSON
                                       │
                                       └─ 索引里的 data_key (32 B, 随机生成)
                                                │
                                                └─ AES-256-GCM 加解密数据区
```

**为什么数据密钥要和口令解耦？**

1. 改口令只需要用新 KEK 重新加密一次索引（几百字节），一个 32 GB 的容器改口令
   是毫秒级的，而不是整盘重写几小时。
2. 数据密钥只以密文形式存在于索引中，索引又由口令派生的密钥保护。忘记口令 =
   数据在密码学上无法恢复，程序里不存在任何后门或恢复通道。

---

## 4. 数据区

数据区是若干**分块记录**的拼接。同一个条目的记录连续存放，条目的首记录相对
`data_offset` 的偏移记录在索引里。

### 分块记录

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 12 | `nonce`（随机，每块独立） |
| 12 | 4 | `ct_len` = 明文长度 + 16 |
| 16 | `ct_len` | AES-256-GCM 密文 |

明文的切分规则：按 `chunk_size`（索引中的 `chunk_size` 字段，默认 1 MiB）切分；
最后一个分块可以更短。如果条目大小恰好是 `chunk_size` 的整数倍，则**不会**产生
一个空的尾块。空文件（大小 0）不产生任何记录。

### 分块的 AAD

每块的 AAD 是：

```
AAD = chunk_id ‖ big_endian_u64(seq)
```

* `chunk_id` 是索引中该条目独有的 16 字节随机标识；
* `seq` 是该条目内分块的序号，从 0 开始。

这个设计保证了：

* 攻击者**不能**把 A 文件的某个分块搬到 B 文件里（`chunk_id` 不匹配）；
* 攻击者**不能**调换同一文件内分块的顺序，也不能删除中间的块然后拼接
  （`seq` 不匹配），因为每条记录的 `ct_len` 是自描述的，删块会导致后续
  `seq` 对不上。

注意分块是独立认证的，**没有**跨块的全局完整性保护。删除整个文件尾部若干个
完整分块不会被分块级校验发现，但解出的明文长度会小于索引记录的 `size`，
解包程序必须据此报错（参考实现就是这样做的），另外每个条目的 SHA-256 也能
兜住这种情况。

## 5. 索引 JSON

索引本身也**不要**当成可信数据——它虽然被 GCM 保护，但解包程序仍然必须校验
条目名等字段（参考实现里的 `safe_relative_name()` 会拒绝绝对路径、目录穿越、
Windows 保留设备名）。

```jsonc
{
  "ulocker": 1,                            // 索引格式版本
  "name": "我的加密库",                     // 显示名
  "created": "2026-10-03T15:45:00+08:00",  // ISO 8601
  "updated": "2026-10-03T16:02:11+08:00",
  "chunk_size": 1048576,                   // 明文分块大小
  "kdf": { "id": 1, "name": "argon2id" },  // 仅作展示，权威值在头部
  "data_key": "Base64(32B)",               // ★ 全容器唯一的机密
  "weak_password": false,                  // 创建时口令是否过短（提醒用）
  "drive": {                               // 为 null 表示未绑定
    "serial": "1A2B3C4D",                  // 卷序列号，绑定判据
    "label": "KINGSTON",
    "filesystem": "exFAT",
    "kind": "removable",
    "root": "E:\\"
  },
  "entries": [
    {
      "name": "项目文档/需求v1.txt",         // 相对路径，'/' 分隔
      "size": 2400,                        // 明文字节数
      "offset": 0,                         // 首块记录相对 data_offset 的偏移
      "chunk": "9f3c…",                    // 16 字节 chunk_id 的十六进制
      "sha256": "a1b2…",                   // 明文 SHA-256（解包时校验）
      "mtime": 1759489500.123,             // 修改时间（Unix 秒）
      "mode": 420,                         // 权限位（Windows 上仅作记录）
      "dir": false                         // 保留字段
    }
  ]
}
```

索引在写入前会尝试 zlib 压缩（压缩有效时置 `ZLIB` 标志位）。文件名用
`ensure_ascii=False` 序列化，所以中文名在解密后是可读的 UTF-8。

---

## 6. 容器内不可变的量

以下内容一旦容器创建就不再改变，除非整体重写：

* `data_key`——**永远不变**。改口令不会换数据密钥，这正是不用重写数据区的原因。
* 数据区里已有的分块记录——追加只会往末尾写，删除会整体重排一次。
* `chunk_size`——只影响新写入的分块；实际读取以索引中的值为准。

## 7. 版本演进策略

* `version` 字段（头部偏移 8）是**不兼容**变更的门槛。遇到不认识的版本，
  实现必须拒绝打开，而不是猜测解析。
* 新增可选字段应放进索引 JSON，并依赖 `ulocker` 字段（索引格式版本）区分；
  老实现遇到不认识的键会忽略，遇到不认识的索引版本会拒绝。
* `flags` 中的保留位在未定义前必须写 0，读取时忽略。
